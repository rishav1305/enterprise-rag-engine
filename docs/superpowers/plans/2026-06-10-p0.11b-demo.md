## 🔴 GATE A — ENTRY-POINT LEAK COVERAGE (per-HTTP-endpoint)
Every backend entry point the demo UI exposes MUST have a passing END-TO-END leak test
**against the actual HTTP call path (FastAPI `TestClient`, NOT `pipeline.query()`)** —
the real path includes the header→`Session` derivation. Classify each demo feature:
  - **routes through `POST /query`** (already e2e-proven at the pipeline; needs its HTTP
    e2e leak test) — the SAFE core; the persona switcher is `/query` with different
    `X-Clearance`/`X-User-Roles` headers.
  - **new endpoint** (e.g. warehouse/SQL) → ships WITH its own biting e2e leak test
    (incl. the deny short-circuit) over HTTP, or it does NOT ship.
  - **read-only metadata** (funnel numbers, oracle result) → still enumerated; assert it
    carries no restricted content.
**No entry point reaches the UI without its own e2e leak test that BITES.**

## 🔴 GATE B — OPERATIONAL DEPLOY-SECURITY (build now, verified live at 11c)
Outside the leak oracle — the review net can't catch these.
- **B-cap — rate-limit + per-session/day query cap.** The demo API is a PUBLIC URL backed
  by live keys; PERFORMANT is scoped 1-user. A config-driven limiter (requests/min +
  per-session/day cap) BEFORE any LLM/embedding call. 429 on exceed. Tested (counting +
  refusal with fake providers; enforced against live creds at 11c).
- **B-synthetic — synthetic-data-only refuse-to-start.** A startup assertion that the
  demo profile reaches ONLY synthetic sources (Meridian corpus + public NYC-TLC/GDELT) —
  refuse to start if a non-synthetic source is configured. A leak in synthetic data is
  theater; against real data it's not. Config + test.
- **B-secrets — server-side-only + client-bundle scan.** ALL LLM/DB/embedding creds in
  the FastAPI server only. A test/check that NO secret is `NEXT_PUBLIC_*` or in the
  client bundle. (The bundle scan runs WITH the FE build — B6.)

## Increment order (each: failing test → build → mutation-prove → ci-green → commit → push)
- **B0 — endpoint inventory + the env-var/secret SCHEMA doc** (every config knob, which
  are secrets, which are server-only). The Gate A checklist is the contract.
- **B1 — `POST /query` HTTP e2e leak + self-escalation tests (TestClient).** Under-cleared
  persona can't retrieve restricted over HTTP; a role/clearance in the request BODY is
  IGNORED (server derives Session from headers only — the untested api.py claim); can't
  forge clearance beyond entitlement. Mutation: trust the body role → self-escalation.
- **B2 — `GET /personas`** (read-only switcher metadata; no restricted content).
- **B-cap — rate-limit + per-session/day cap** (config + middleware/dependency + 429 test).
- **B-synthetic — synthetic-only refuse-to-start** (config profile + startup assertion + test).
- **B3 — `POST /warehouse`** IF the demo exposes governed SQL — with the biting HTTP e2e
  leak test (deny→no-rows, mask→redacted). Else: explicitly NOT exposed, documented.
- **B4/B5 — `GET /glossary` + `GET /funnel`** read-only metadata endpoints + tests.
- **B6 — Next.js demo in portfolio_app** (persona switcher, leak-oracle result, funnel viz,
  glossary, provenance/citations, cost/token) + the **client-bundle no-secrets scan** +
  FE build verification. (Verify portfolio_app structure first; this is the FE-side work
  outside `make ci`.)
